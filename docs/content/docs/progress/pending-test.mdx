# Pending Tests

The current release needs manual verification in these areas:

- Credit conversion (`/wallet`): converting N credits should deduct them immediately, add an `exchange` ledger row, and list a `pending` record — the gateway grant is not wired yet, so `pending` is the expected end state, not a failure. Converting more than the available balance must be rejected, and frozen escrow credits must not be spendable. Once `/gw` is wired, a failed grant must refund the credits and show `failed`.
- Job deadlines and deposits: posting now takes a delivery window and an overall validity. Accepting a quote freezes the client's quote amount **and** a 5-credit deposit from the creator. Verify each expiry path (set the deadline into the past in the DB, then wait one sweep or restart the server): (1) delivery window passes while `active` → deposit forfeited 2-to-client/3-to-platform, the late creator's quote is deleted, other quotes survive, the job returns to the hall, and the **client's credits stay frozen**; (2) review window passes while `submitted` → auto-accepted and paid out, deposit returned; (3) overall validity passes while open/quoted/active → job voided, client refunded, deposit returned untouched. A `submitted` job must NOT be voided by the overall validity.
- Re-accept then cancel: accept a 60 quote → let the delivery window lapse → accept a cheaper 40 quote (the client's frozen amount drops to 40) → cancel the job. The cancel must succeed; it used to fail with a duplicate-key error on `wallet_ledger` because both the delta release and the final release wrote an `unfreeze` row under the same ref.
- Job deposit edge cases: a creator with under 5 available credits cannot be accepted; re-accepting a different quote after a timeout adjusts the client's frozen amount by the difference (40 → 45 freezes 5 more, 40 → 30 releases 10); repeated sweeps must not pay out or forfeit twice.
- Jobs escrow needs **two accounts** now that roles come from the signed-in user: account A posts a job, account B quotes, A accepts (B's quote freezes A's credits), B delivers, A rejects then accepts — B's balance should rise by the quote minus the 10% platform fee, and A's frozen amount should return to zero. A single account can no longer play both sides; quoting your own job is rejected server-side.
- Jobs brief and delivery images: images inserted into a job brief are still stored in the poster's own browser (`image:<key>` refs resolved from local IndexedDB), so **another account sees broken images**. Verify after the images move to object storage.
- Jobs detail privacy: a signed-in user who is neither the poster nor the assigned creator (including someone who quoted but lost the bid) must see the title/brief/budget/status but **not** the delivery content, delivery link, or settlement figures — settle cost and platform profit especially. Check both `GET /api/jobs/:id` and the 我接的 list.
- Jobs list scopes: 工作大厅 shows only `open`/`quoted`; 我发布的 shows jobs you created; 我接的 shows jobs you quoted on or were assigned. Deep-linking a job you have no part in should still render read-only with no action buttons.
- Recharge service (`server/`) self-checks: `npm run check:alipay` should reject a swapped app-public-key/Alipay-public-key pair and otherwise print a signed cashier URL; `npm run check:db` should connect and create `recharge_orders` / `user_wallets` / `wallet_ledger`. With neither Alipay nor MySQL configured the service must still start and `/health` report both as false.
- Recharge happy path (`/wallet`): sign in → pick a tier → Pay with Alipay opens the cashier in a new tab → pay → the page flips to success within a few seconds without a manual refresh, balance and credit history both update, and the top-up shows as `paid`. Repeat with the popup blocked: the in-modal cashier link must still work.
- Recharge amount safety: `POST /pay-api/api/pay/orders` must ignore any amount in the request body — only `packageId` is honoured, and an unknown id returns 400. A tampered tier price on the client must not change what Alipay charges.
- Recharge exactly-once: replay the same Alipay notify body twice (or let the notify, the frontend poll, and the reconcile loop all fire for one order) — the order must credit exactly once, the second attempt logging「重复通知，忽略」with no second `wallet_ledger` row.
- Recharge notify rejection: a POST to `/api/pay/notify` with a bad signature, a foreign `app_id`, an unknown order number, or a mismatched `total_amount` must be rejected and must not credit anything.
- Recharge without notify: set `ALIPAY_NOTIFY_URL` empty, pay, then close the tab before it lands — the background reconcile loop should credit the order within `RECONCILE_INTERVAL_SEC`.
- Recharge auth: `/api/wallet` and the order endpoints must 401 without a valid MaaS token; one user must not be able to read another user's order by guessing `out_trade_no` (expect 404, not 403).
- Navigation gating: 「积分充值」and「配置」should be hidden from both the top bar and the mobile drawer when signed out, and appear after login; deep-linking `/wallet` while signed out shows the sign-in prompt rather than an error.
- Deployment wiring: with `PAY_UPSTREAM` unset on Vercel, `/pay-api/*` must return a 503 JSON message rather than the SPA `index.html`; with it set, the wallet page works end to end on the deployed domain.
